## Общая основа

`integration/current-baseline` создана от указанного main. Formats принята
обычным merge с сохранением истории: она уже содержит backend, поэтому
повторный перенос backend не нужен. Итоговые API, сервис, repository, модели,
миграции и ingestion взяты целиком из formats. Исходные ветки не удаляются.

## Выборочные переносы

После принятия основы новые ветки создаются от обновлённого main:

- `refactor/agent-instructions`: адаптация системных инструкций из
  `feature/sergey-langgraph` под существующий LLMClient, FactCheckResult
  и TokenUsage. Старые глобальные счётчики, SQLAlchemy-слой и runner не нужны:
  эти обязанности уже реализованы общей основой.
- `feat/dashboard-api`: вкладки старого dashboard, работающие через HTTP API.
  Прямой вызов runner и сброс глобальных счётчиков исключаются, чтобы UI
  использовал ту же очередь, историю и обработку ошибок, что и другие клиенты.

Учебная ветка langgraph-basics не содержит рабочего анализа. Отдельная БД из
sergey-gradio не переносится. Если нужны её существующие данные, потребуется
отдельный согласованный импорт: миграция новой схемы не доказывает совместимость
со старой SQLAlchemy-схемой.

## Требования к будущей проверке качества

Инструкции адаптируются из f626238 и 7d64f44: system/user разделены в SDK,
а backend-контракты `FactCheckResult` и `TokenUsage` сохранены. Если summary
уже существует, он передаётся фактчекеру; чанковый граф работает без него.
Требование старой ветки выводить три текстовых заголовка не переносится:
структура JSON задаётся действующей схемой. Один существующий JSON-repair
сохранён, включая учёт токенов обеих попыток. Улучшенные инструкции сами
по себе не гарантируют устойчивость к prompt injection или качество ответов.

Дефектный quality_gate из 7d64f44 не переносится. Будущая реализация должна:

- проверять структуру утверждений и ссылки на исходник, а не подстроки статусов;
- отличать успешное выполнение задачи от качества результата;
- проверять публикуемые утверждения summary/final и объединение длинных документов;
- ограничивать число исправлений и явно завершаться passed/needs_review/failed;
- не выдавать исчерпание повторов за успешную проверку.

Это требования следующего этапа, а не реализованные гарантии текущего API.

## Проверка и откат

Общая основа проверяется всеми offline-тестами, Postman JSON и HTTP smoke-сценарием
mock API. Реальные запросы GigaChat не требуются. Реальный .env не добавляется;
старый секрет в истории этим слиянием не удаляется и не проверяется на действительность.

Каждый из трёх PR принимается отдельным merge-коммитом. Для отката последнего
изменения применяется `git revert -m 1 <merge-коммит PR>` через новый PR.
Нельзя одновременно откатывать внешний PR-merge и его внутренний merge.
Если уже приняты зависимые изменения, откатывать их нужно в обратном порядке
либо делать совместимое исправление вперёд. Общую историю не переписывать.

Кодовые откаты не являются откатами БД. При проверках используются отдельные
временные базы; существующие локальные данные не очищаются.
