# Контракты агентов v1

База: main `6306124` после PR #59. Здесь фиксируется существующий обмен данными,
а не качество ответов GigaChat. Для параллельной разработки можно менять промпты
и реализацию агента, сохраняя приведённые входы и выходы.

## Что называется контрактом

Агент получает Python-словарь с входными данными и возвращает словарь изменений
состояния (patch). LangGraph объединяет patch с остальным состоянием. Поэтому
Summary возвращает `summary`, а не полный документ и не поле `abstract`.

Общие технические входы пяти LLM-узлов:

- `llm: LLMClient` — клиент внешней модели, а не текст для передачи соседнему агенту;
- `token_usage: TokenUsage` — уже накопленный расход запуска.

На границе узла данные и статистика копируются; объект клиента переиспользуется.
Узел получает только свои объявленные поля, возвращает полный обновлённый
`token_usage` и может увеличивать только собственную строку `by_agent`.
Изменения применяются через возвращённый patch. Сбрасывать накопленные значения
или повторно добавлять расход предыдущих узлов нельзя.

## Входы и выходы

В таблице технические входы `llm` и `token_usage` подразумеваются для каждого узла.
Каждый из пяти узлов также возвращает `token_usage: TokenUsage`.

| Узел / функция | Обязательные данные | Необязательные данные | Поле результата | Имя в by_agent |
|---|---|---|---|---|
| Analyzer / `analyzer` | `text: str` | — | `analysis: str` | `Analyzer` |
| Summary / `summary` | `analysis: str` | — | `summary: str` | `Summary` |
| Fact Checker / `fact_checker` | `text: str`, `analysis: str` | `summary: str`, без поля используется пустая строка | `fact_check: FactCheckPayload` | `Fact Checker` |
| Final / `final_agent` | `analysis: str`, `summary: str`, `fact_check: FactCheckPayload` | — | `final: str` | `Final` |
| Final Verification / `verify_final` | `source_chunks: list[SourceChunk]`, `final: str` | `summary: str` | `final_review: FinalReviewDraft` | `Final Verification` |

Metadata и промежуточные результаты других узлов остаются в общем состоянии,
но не передаются агенту, который их не объявил. Например, Final получает результат
Fact Checker, а Summary использует только analysis. Для доступа к дополнительному
полю требуется согласованное изменение контракта.

Analyzer, Summary и Final возвращают обычные строки. Не требуется превращать их
ответы в новый JSON. Содержание и формулировки строк не фиксируются эталоном;
пустая строка структурно допустима в v1, но может быть ошибкой качества.

## Структурированный фактчек

`FactCheckPayload` после разбора ответа модели содержит все четыре поля:

```json
{
  "verification_summary": "Утверждение о бюджете не подтверждено",
  "doubtful_claims": ["Фактические расходы составили 10 млн рублей"],
  "contradictions": [],
  "neuroslop": {
    "probability": 0.2,
    "explanation": "Эвристическая оценка качества исходного текста"
  }
}
```

- `verification_summary`: строка;
- `doubtful_claims`, `contradictions`: списки строк, включая пустые списки;
- `probability`: число от 0 до 1;
- `explanation`: непустая строка.

Модель возвращает JSON как строку `LLMAnswer.content`. Fact Checker разбирает
его через существующий `FactCheckResult`. Пропущенные моделью списки получают
существующие значения по умолчанию `[]`; на выходе узла поля уже присутствуют.
Сохранён один дополнительный запрос исправления JSON. При повторной ошибке —
`PipelineError`; в расход входят обе полученные от модели попытки.

FactCheckPayload передаётся между узлами без дополнительных неизвестных полей.
Пустой `{}` вместо результата проверки для Final не является допустимым входом.
Одну прежнюю тестовую заглушку с `{}` заменили полноценным существующим форматом.

## Проверка итогового отчёта

Final Verification переиспользует `fact_checker`: вместо проверяемого analysis
подставляет `final`, вместо источника — `source_chunks[0].text`. Если есть summary,
он также передаётся. Первичный `fact_check` не перезаписывается.

У двух проверяющих самостоятельные контракты. `FactCheckPayload` включает оценку
нейрослопа исходного документа. `FinalReviewDraft` содержит только
`verification_summary`, `doubtful_claims`, `contradictions`: его задача —
соответствие готового отчёта исходнику. Тип не наследуется от FactCheckPayload.
Общая реализация fact_checker пока остаётся за адаптером verify_final;
адаптер выбирает только поля контракта итогового проверяющего. Затем
детерминированный узел добавляет `status`, получая `FinalReviewState`:

- непустой doubtful_claims **или** contradictions → `needs_review`;
- оба списка пустые → `no_flags`.

В публичном API и PipelineResult используется уже существующая модель
`FinalReview`. Формат API не меняется:

```json
{
  "verification_summary": "Проверка готового отчёта",
  "doubtful_claims": ["Неподтверждённый вывод в отчёте"],
  "contradictions": [],
  "status": "needs_review"
}
```

Разрешённые значения статуса: `not_evaluated`, `no_flags`, `needs_review`.
Сейчас многочанковый путь возвращает `final_review: null`; старые записи тоже
могут не содержать этого поля. Интерфейс показывает отсутствие проверки явно.
`completed` — технический статус задачи, `needs_review` — оценка качества.
`no_flags` означает отсутствие замечаний модели, а не доказательство истинности.

`SourceChunk` имеет только `chunk_id: str` и `text: str`. Список источников
непустой. В текущем коротком графе это один контейнер всего текста. Страницы,
смещения и проверяемые ссылки этим контрактом не обещаются.

## Клиент модели

```python
ask(prompt: str, *, system_prompt: str = "") -> LLMAnswer
count_tokens(text: str) -> int
```

`LLMAnswer` содержит `content: str` и `usage: TokenCount`. В TokenCount три
целочисленных поля: input_tokens, output_tokens, total_tokens. TokenUsage
содержит эти же итоговые поля и `by_agent: dict[str, TokenCount]`.
Это Python-объекты, поэтому вход агента не является целиком JSON-документом.

## Как проверять свой агент отдельно

```python
from multi_agent_docs.agents.summary import summary
from multi_agent_docs.llm.mock_client import MockLLMClient
from multi_agent_docs.models import TokenUsage

result = summary({
    "analysis": "Бюджет планируется в размере 10 млн. Фактические расходы неизвестны.",
    "llm": MockLLMClient(),
    "token_usage": TokenUsage(),
})
assert set(result) == {"summary", "token_usage"}
```

Этот пример проверяет совместимость кода. Для оценки качества используйте
реальную модель и размеченные примеры. Можно менять текст prompt/system_prompt,
выбирать контекст и внутренний алгоритм, оставаясь в согласованном интерфейсе.
Запрос дополнительного поля или изменение формата результата — отдельное
контрактное изменение с проверкой потребителей.

## Что защищает реализация

1. `agent_contracts.py`: TypedDict входов/выходов и общая схема состояния.
2. `@agent_node`: проверка обязательных входов и типов, изоляция входных данных,
   запрет лишних/переименованных выходных полей и изменения чужого расхода.
   Ошибка контракта даёт существующий PipelineError; текст документа в сообщение
   ошибки не включается.
3. `contracts/v1.json`: зафиксированные схемы данных, сигнатуры LLM и узлов,
   доступные поля, владельцы статистики и связи графов.
4. `tests/test_agent_contracts.py`: сравнение кода с эталоном и негативные примеры.
   Текущий CI автоматически запускает этот файл обычным pytest.
5. `AGENTS.md`: правила сохранения интерфейсов и согласования изменений с командой.

Полезные формулировки ответов не фиксируются. Изменение описаний JSON Schema
также не считается изменением структуры. Автоматического обновления эталона
при тестах нет. Новые поля, переименование, типы, defaults и маршруты потребуют
явного изменения эталона и обсуждения совместимости.

## Процесс изменения

Для обычной работы с агентом не трогайте общие модели, сигнатуры, JSON-эталон
и контрактные проверки. При необходимости изменить интерфейс:

1. Описать причину, потребителей и совместимость со старыми данными.
2. Обновить связанные входы/выходы и тесты обоих участников обмена.
3. Явно согласовать изменение эталона v1; для несовместимой следующей версии
   согласовать версию v2 и переход, а не просто повысить номер ради зелёного CI.
4. Согласовать изменение с другим участником перед слиянием. PR создавать
   только по прямой просьбе пользователя.

Команда пока работает на доверии: CODEOWNERS и обязательные серверные одобрения
не используются. Runtime-проверки и тесты обнаруживают нарушения интерфейса,
а изменения самого эталона и тестов согласовываются организационно.
Эталон и AGENTS.md не являются запретом на осознанную правку кода и проверок.
