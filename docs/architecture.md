# Архитектура backend MVP

## Слои

```text
HTTP / FastAPI
      ↓
AnalysisService + однопоточная очередь
      ├──→ runner → LangGraph → agents → GigaChat
      ↓
DocumentRepository
      ↓
SQLite
```

FastAPI отвечает только за HTTP: потоковую загрузку, HTTP-валидацию и схемы ответов. Он обращается к истории и запускает анализ исключительно через `AnalysisService`.

`AnalysisService` регистрирует задачу, передаёт её единственному фоновому worker и сохраняет результат либо безопасную ошибку. Незавершённые задачи после рестарта переводятся в `failed`.

Runner извлекает текст, проверяет лимит токенов и запускает LangGraph. Большие документы разбиваются на чанки; результаты объединяются редьюсерами. Исходный файл удаляется после завершения задачи.

После подготовки текста и фрагментов runner вызывает единый `document_app`.
Управляющий граф из `orchestration.py` выбирает `app` для одного фрагмента
или последовательно вызывает `chunk_app` для нескольких. Затем узел
`reduce_results` объединяет частичные результаты, а `synthesis_app` создаёт
общую сводку и итоговый отчёт. Обработка фрагментов остаётся последовательной.

Схема SQLite изменяется только версионируемыми Alembic-миграциями. На старте сервис выполняет `upgrade head`; прямого `CREATE TABLE` в runtime-коде нет.

## Режимы LLM

- `APP_MODE=real` — настоящий `GigaChatClient`;
- `APP_MODE=mock` — детерминированный `MockLLMClient` без сети.

Оба режима используют одинаковые transport, business, repository и LangGraph. Благодаря этому сквозные API-тесты подменяют только внешнюю модель, а не внутренний pipeline.

## Состояния задачи

```text
queued → running → completed
                 ↘ failed
```

`completed` описывает техническое завершение обработки. Замечания к содержанию
не меняют статус выполнения на `failed` или `needs_review`. Качество итогового
отчёта передаётся отдельно в `results.final_review.status`.

## Проверка итогового отчёта

В одночанковом пути `app` выполняет первичную проверку анализа и сводки
(`fact_check`), создаёт `final`, затем выполняет отдельную проверку готового
отчёта (`final_review`). Последняя использует существующий `fact_checker`
с копией состояния: в качестве проверяемого анализа передаётся `final`,
исходным текстом служит `source_chunks[0].text`.

Первичный `fact_check` сохраняется независимо. Итоговый статус выбирается
только по спискам замечаний в `final_review`: хотя бы один непустой список
`doubtful_claims` или `contradictions` даёт `needs_review`, оба пустые —
`no_flags`. Чистый первичный фактчек не отменяет замечания к итогу; чистая
итоговая проверка не удаляет первичные замечания. `no_flags` означает отсутствие
замечаний у проверяющей модели и не является доказательством достоверности.

В многочанковом пути проверяются отдельные фрагменты, затем сводятся результаты
и генерируются общие сводка и итог. Отдельной сверки сгенерированного итога со
всеми исходными фрагментами пока нет: `final_review` остаётся `None`, в API —
`null`. Сводные результаты первичных проверок не подставляются вместо него.
Это ограничение явно отображается в UI как «Итоговый отчёт не проверен».
Такое же предупреждение показывается для старых результатов без этого поля.
Состояние `not_evaluated` также показывается как непроведённая проверка.

На вкладке «Итог» Gradio отдельно выводятся статус итоговой проверки и оба
списка замечаний. Первичная проверка остаётся на вкладке «Факты»; статус
выполнения находится в отдельном поле. До получения результата поля качества
пустые, а не помеченные как успешно проверенные.

## Что делает prepare_sources

`prepare_sources` в коротком графе проверяет непустоту текста и кладёт весь
входной `text` без изменений в единственный элемент
`{"chunk_id": "chunk_0001", "text": text}` списка `source_chunks`.
Узел не разбивает документ на несколько частей. Реальное разбиение выполняет
`ingestion.chunking.split_document` до запуска управляющего графа.

`chunk_0001` — локальный идентификатор контейнера текста. Здесь нет номеров
страниц, символьных смещений, постоянных ссылок на исходный файл и проверяемых
цитат. Идентификаторы чанков управляющего графа также не заменяют ссылок на
конкретные места оригинала. Исходный файл остаётся временным и удаляется
сервисом после обработки.

## Публичный API

- `POST /analyze` — регистрация фонового анализа;
- `GET /documents` — страница истории;
- `GET /documents/{id}` — статус или полный результат;
- `GET /health` — проверка SQLite и worker;
- `GET /docs` — Swagger UI.

Gradio является необязательным HTTP-клиентом backend. Он отправляет документ
через POST /analyze, получает статусы и результаты через GET /documents/{id}
и не импортирует runner, LLM-клиент или слой хранения. UI и backend запускаются
отдельно; дополнительная очередь или второй pipeline в UI не создаются.
